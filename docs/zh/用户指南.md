# 1 a2a-t-sdk-python 用户指南

## 1.1 特性介绍
### 1.1.1 什么是A2A-T？
A2A-T（Agent-to-Agent Telecom）是基于A2A协议推出的电信领域多智能体互联协议，专为电信领域复杂协同场景设计。
业界通用智能体互联协议主要关注智能体互联和交互框架，对业务场景和具体交互内容关注不足，导致任务完成的成功率不高。电信领域的业务场景复杂、要求高，运维智能体互联和协同需要有专门的协议进行支撑。A2A-T方案基于A2A协议，重点针对电信领域业务流相关的信息模型、任务协商、协作安全等增强能力进行应用扩展。

### 1.1.2 A2A-T SDK与A2A SDK的关系
 
A2A-T协议是基于A2A协议的扩展，针对协议扩展的内容提供了A2A-T SDK，支撑快速构建满用于电信领域复杂协同场景的智能体。A2A-T SDK独立于A2A SDK，通过同时集成A2A-T SDK与A2A SDK可以构建支持A2A-T协议的agent，支持电信领域多agent之间的确定性、高可靠、高效及安全协同。

### 1.1.3 能力介绍

a2a-t-sdk-python是面向电信智能体协作场景的 Python SDK，用于在 A2A-T 交互中生成、校验和协商任务提示词。SDK 适合客户端 Agent、服务端 Agent 以及上层编排系统集成使用。

主要能力包括：

- **任务提示词生成**：客户端根据自然语言或结构化输入生成符合 A2A-T 格式的 processed task prompt。
- **服务端提示词校验**：服务端校验客户端下发的 processed task prompt 是否匹配场景、模板和槽位约束。
- **多轮协商**：支持`information`协商流程。
- **提示词资源管理**：内置场景、槽位、模板和系统提示词资源，支持本地文件资源加载。
- **LLM 适配**：通过 OpenAI-compatible 调用链接入外部大模型。

### 1.1.4 “协商（negotiation）”概念说明

A2A 生态中存在两种语境下的“协商”，含义不同，需注意区分。

**A2A 扩展激活（extension activation）中的协商**

A2A 协议中，扩展通过声明式机制激活：客户端在请求头 `A2A-Extensions` 中声明本次请求要使用的扩展 URI，服务端依据 AgentCard 中声明的扩展（可标记 `required: true`）进行校验，若客户端未声明服务端必需的扩展，则返回 `ExtensionSupportRequiredError`。此处的“协商”是面向**协议能力**的握手——双方就“启用哪些协议扩展”达成一致，单次声明校验即可完成，不涉及具体业务内容，由 A2A 协议框架处理。

**A2A-T 中的协商（negotiation）**

A2A-T 中的 negotiation 指的是**多智能体间协商机制的实现**：当任务信息不足、任务目标不清晰或能力可行性需要确认时，客户端与服务端围绕任务提示词的内容进行多轮往返交互，逐步补齐缺失信息，最终达成一致的任务提示词。该机制由本 SDK 的协商引擎实现，包括协商类型（当前内置 `information`）、协商接口（`start_negotiation`、`receive_negotiation`、`continue_negotiation`）以及协商状态机与状态存储。

两者差异对比：

| 维度 | A2A 扩展激活中的协商 | A2A-T 中的协商 |
|--|--|--|
| 层次 | 协议层（能力） | 业务层（任务内容） |
| 协商对象 | 扩展 URI 是否启用 | 任务提示词是否完整、清晰、可执行 |
| 交互方式 | 声明式单次校验（不匹配返回 `ExtensionSupportRequiredError`） | 多轮往返，逐步补齐信息直至达成 |
| 交互载体 | `A2A-Extensions` 请求头 / AgentCard 扩展声明 | A2A 消息扩展字段（Task-T / NEGOTIATION-T / DATA-NEGOTIATION-T）及协商上下文 |
| 实现主体 | A2A 协议框架 | 本 SDK 的协商引擎 |

简单来说：A2A 扩展激活中的 negotiation 是“协议能力是否启用”的握手；A2A-T 中的 negotiation 才是多智能体间围绕任务达成进行的协商机制的实现。

## 1.2 应用场景

Python SDK 通常用于以下场景：

1. 客户端 Agent 接收用户意图，生成结构化任务提示词后通过 A2A 协议发送给目标 Agent。
2. 服务端 Agent 接收任务提示词，执行格式、场景和槽位校验，再进入业务处理。
3. 当任务信息不足、任务目标不清晰或能力可行性需要确认时，双方通过 SDK 协商接口推进多轮交互。

## 1.3 环境要求

| 项目         | 要求                            |
|------------|-------------------------------|
| Python SDK | Python 3.12+                  |
| 依赖管理       | 推荐使用 `uv`                     |
| LLM        | 需要可访问的 OpenAI 服务及 API Key     |
| 操作系统       | Linux、Windows、macOS 均可用于开发和联调 |

## 1.4 安装

### 1.4.1 源码方式安装 SDK

```bash
cd {项目路径}/a2a-t-sdk-python
uv sync --dev
```

执行测试确认环境可用：

```bash
uv run pytest
```

### 1.4.2 准备 SDK 配置

复制环境变量模板：

```bash
cd {项目路径}/a2a-t-sdk-python
cp package_data/env.example package_data/.env
```

至少需要配置以下内容：

```properties
A2AT_LANGUAGE=zh-CN
A2AT_PROMPT_SOURCE_TYPE=local_file
A2AT_PROMPT_RESOURCE_LOCAL_ROOT_DIR=
A2AT_PROMPT_COMPLIANCE_ENABLED=true
A2AT_LLM_PROVIDER=deepseek
A2AT_LLM_MODEL=deepseek-chat
A2AT_LLM_API_KEY={your_api_key}
A2AT_LLM_BASE_URL=https://api.deepseek.com
A2AT_NEGOTIATION_STATE_STORE_TYPE=in_memory
```

如果 `A2AT_PROMPT_RESOURCE_LOCAL_ROOT_DIR` 为空，SDK 默认使用包内资源。需要使用自定义场景、槽位或模板时，将该配置指向自定义资源根目录。

## 1.5 配置文件速查

| 配置项                                   | 说明                             |
|---------------------------------------|--------------------------------|
| `A2AT_LANGUAGE`                       | 提示词资源语言，当前常用 `zh-CN` 或 `en-US` |
| `A2AT_PROMPT_SOURCE_TYPE`             | 提示词资源来源，当前支持 `local_file`      |
| `A2AT_PROMPT_RESOURCE_LOCAL_ROOT_DIR` | 自定义提示词资源根目录                    |
| `A2AT_PROMPT_COMPLIANCE_ENABLED`      | 是否启用服务端提示词合规校验                 |
| `A2AT_LLM_PROVIDER`                   | LLM 提供方                        |
| `A2AT_LLM_MODEL`                      | 模型名称                           |
| `A2AT_LLM_API_KEY`                    | LLM API Key                    |
| `A2AT_LLM_BASE_URL`                   | LLM 服务地址                       |
| `A2AT_NEGOTIATION_STATE_STORE_TYPE`   | 协商状态存储，当前支持 `in_memory`        |

## 1.6 约束与限制

1. 内置协商状态存储为内存实现，不提供持久化能力。
2. 提示词资源当前以本地文件为主，不包含注册中心远程资源加载能力。
3. SDK 负责 A2A-T 提示词生成、校验和协商，不负责 AgentCard 注册、鉴权、服务托管和业务执行。
